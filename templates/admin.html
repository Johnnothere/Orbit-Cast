Source health

Every source feeding the catalogue and what it contributed on the last scrape, post-filter. A source on 0 used to be unreadable — dormant and broken looked identical. Each row now carries when it last returned anything and the last error it raised, so "0 events, last worked 11 days ago" is a fact you can act on. Pause stops a source being scraped at all, for the built-in sources as well as the Luma organisers.

Add a recurring organiser

Paste any Luma organiser link — a calendar (lu.ma/cal-…), a vanity URL (luma.com/londonai), or a host profile (luma.com/user/…). It is checked against their real upcoming events before anything is written.

Tracked organisers

Approved from here and scraped every refresh. Pausing keeps the record but stops the scrape — a quiet organiser is not a dead one.

Discovered leads

Organisers the scraper found hosting events we already ingest, or on Luma's London feed. Proposals only — nothing here feeds the catalogue until you add it. The queue is paginated against a real total, decisions apply optimistically without refetching the list, and anything you accept or reject is written to the audit trail.

Add an event by link

Paste the event's own page. It gets fetched, read, and checked against the catalogue rules — London or genuinely online, upcoming, a real event page, not an aggregator card, not already listed. If every check passes it goes straight in.

Events added by link

Re-emitted into the catalogue on every scrape, and they drop off on their own once the date passes.

Live catalogue

Everything currently being served. A bad scraped event could not be touched from here before — only manually added ones could be removed. Hiding one drops it from the catalogue immediately and keeps it out of every future scrape, and it can be restored below.

Hidden events

Suppressed by hand. They stay out of the catalogue, the calendar and the scorer until restored.

Accounts

Google sign-in made the account the real identity, and nothing in the panel could show you one. This is every account row: who it is, when they joined, their digest state, saved events, and how many analyses they have run.

Look up a specific visitor

Paste an oc_uid to see everything tied to that browser, or click any row below.

All visitors

Everyone ever asked for consent, most recently active first. A decline shows zero activity by design.

Scoring rules

The guidance Claude follows when judging fit. The JSON output format is fixed elsewhere and cannot be broken by editing this.

Add a single example

Describe one person and how an event judgment played out.

Stored examples

The RAG knowledge base. Delete anything wrong or low quality.

Upload a dataset document

A PDF, DOCX or TXT of CV-to-event judgments, even messy notes — Claude structures it into examples automatically.

Scrape

The catalogue refreshes itself every 30 minutes. POST /api/refresh has been admin-only since the October hardening but had no button anywhere in this panel, so a scrape could not be triggered by hand at all. It can now.

Mail

Which provider is configured, which sending address it will use, and whether that address can actually reach anyone. MAIL_FROM defaulting to onboarding@resend.dev only mails the Resend account owner — this is where you find that out before a digest goes nowhere.

Audit log

Sign-ins, refused sign-ins, analyses, exports, CV deletions, account deletions, calendar-feed issues and admin CV downloads. The table has existed since migration 0014 with nothing able to read it.
